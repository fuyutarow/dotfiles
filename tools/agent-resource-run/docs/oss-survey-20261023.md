# GPU admission: existing OSS comparison

Assessment date: 2026-10-23. Proposition: GPU-ADMISSION-OSS-SURVEY-1023.

**Recommendation: keep R1–R4 in the present integration.** Existing schedulers can supply count and declared-budget primitives; this is not evidence that those primitives needed a new implementation. None of the reviewed primary sources establishes a complete replacement under all target constraints. R4 is a plausible small OSS utility, but its detection accuracy and external demand remain unevaluated.

## Scope and method

This is a bounded, single-reviewer primary-source comparison for the owner’s replacement/publication decision, not an exhaustive novelty survey or a hardware compatibility certification. Target: one host, WSL2, one 12 GB consumer NVIDIA GPU, agent commands launched in systemd user scopes, no assumed root daemon, CUDA through dxg. No candidate was installed or executed. Sources below were read on the assessment date; moving branches/documents are identified by retrieval date where no release was established.

Local responsibility definitions were read directly from `tools/agent-resource-run/README.md` (GPU slots, declared reservations, ccc handoff, systemd cleanup ownership) and `tools/shared/GPU-RECOVERY.md` (D-state plus dxg wait channel, persistent wait and recovery). A count means admitted jobs per device, not CUDA contexts or processes. R2 is advisory reservation admission, not physical VRAM enforcement. R3 requires completing a batch, destroying the daemon’s CUDA context, and resuming after research ownership ends; pausing CPU execution is insufficient. R4 is admission refusal on a persistent dxg-blocked task, not general GPU telemetry or a guaranteed diagnosis of every GPU hang.

Matrix terms: **covers** = documented mechanism supplies the responsibility within that tool’s managed workload; **partially** = related mechanism needs adapters or misses a required property; **no** = reviewed primary interface describes a different mechanism and provides no documented implementation of this responsibility. A “no” based on documentation is a bounded finding, not proof that no extension exists. WSL/runtime support not established is explicitly **unevaluated**, independently of conceptual coverage.

Review plan/coverage contract: include all five requested candidate families, official WSL/NVIDIA guidance, and directly discovered single-host/WSL-monitoring alternatives. Extract interfaces and failure semantics, compare mechanisms, then assess integration separately. Search used web queries including `task spooler GPU -g -G slots github`, `Slurm GRES cgroup GPU memory scheduling`, `Ray scheduling GPU memory logical resources`, `NVIDIA MPS WSL support`, `site:github.com WSL dxg hang detector GPU watchdog`, `site:github.com WSL GPU health check watchdog dxg tool`, and `site:docs.nvidia.com "MPS" "WSL" support`. Hits were discovery only; conclusions below use the projects’ own documents. No search result count is treated as evidence of absence. This is a configurative comparison; meta-analysis and statistical evidence grading are not applicable.

## Per-responsibility decisions

| Part | Verdict and one-line integration cost |
|---|---|
| R1 | **keep** — ts/Ray/Slurm could supply count primitives, but queue/runtime adoption and scope-cleanup ownership adapters cost more integration than the existing per-device flock pools; no demonstrated drop-in replacement. |
| R2 | **keep** — gpusched is the closest reuse candidate and Ray can model the arithmetic, but adopting either requires a single admission authority, manifest adapter and proven reservation retention until all systemd descendants exit; WSL behavior remains unevaluated. |
| R3 | **keep** — reviewed tools do not document the ccc-specific batch drain/context destruction/restart protocol; an external scheduler still needs this adapter and ownership handshake. |
| R4 | **keep** — reviewed docs/tools do not establish a rootless persistent D+dxg admission gate; retaining it is justified as a local policy, while its diagnostic accuracy is explicitly unevaluated. |

These are engineering judgments under the supplied constraints, not runtime benchmark results. Replacing only count/budget arithmetic remains possible; a general scheduler would not automatically replace cleanup correctness or driver-health policy. “GPU guard necessary” therefore means these local responsibilities remain necessary for the stated workflow, not that every line of the current implementation is indispensable or correct.

## Could R4 be standalone OSS?

**Plausible niche utility; publication readiness unevaluated.** Likely users are WSL2 CUDA researchers, local inference/embedding-daemon operators and agent/CI launchers sharing a consumer GPU. Existing primary material includes WSL diagnostic guidance, first-person upstream hang reports, WSL2-compatible monitoring, and NVIDIA’s restricted WSL telemetry. This bounded search found no documented equivalent admission classifier; it does not establish novelty or demand.

A useful standalone boundary is a read-only, bounded-time health command that emits healthy / suspected persistent stall / unknown, with PID/TID, process-start identity, wait channel, observation duration and relevant WSL/kernel version. Callers decide admission. It should not kill tasks, reset the Windows GPU or shut down all distros automatically. A monitor that calls CUDA/NVML can itself block; W3 shows nvidia-smi among blocked tasks. Independent process-state inspection and bounded probe ownership therefore matter.

Accuracy needed: one D-state or dxg sample cannot imply a hang. Validate persistence across samples, inspect threads as well as leaders, handle PID reuse and task disappearance, and distinguish unreadable/hidden wait channels from healthy. Generic D-state tasks can be unrelated to GPUs. False positives deny healthy research; false negatives authorize work on a stalled path. Require measured false-denial rate, missed-stall rate and detection latency against labeled healthy long kernels, transient waits, actual stalls, blocked monitors and permission failures across WSL/kernel/Windows-driver versions. There is no evidence here for a defensible numeric threshold. A dxg wait is a symptom, not proof of root cause or a promise that `wsl --shutdown` fixes it [W3]. Publish as an experimental detector with recorded cases first; do not claim a reliable universal GPU watchdog from the current evidence.

The broader guard has publication value chiefly as a documented composition of user-scope lifetime ownership, declared reservations and cooperative context handoff. R1/R2 alone have substantial existing alternatives [T1,S1,Y1,G1]. Whether that composition earns ongoing OSS maintenance is an owner/product decision; external adoption is not measured here.

## Challenges, limitations and unverified items

- Strongest counterexamples were retained: Ray really can account both logical dimensions; gpusched really reserves declarations plus margin; current MPS v3 really documents device-memory cgroup limits. Thus “nothing existing can do this” is rejected. None establishes the complete target integration.
- All source claims are documentation/report evidence. No candidate execution, performance, crash handling, concurrent-client race or WSL compatibility test was authorized or performed. This comparison does not certify the current guard either.
- ts package identity matters: original ts and GPU fork are different artifacts. GPU-fork WSL telemetry behavior and arbitrary per-device N-slot semantics remain unevaluated.
- Ray task completion versus external systemd descendant lifetime, cancellation and user-scope launch permissions remain unevaluated. Encoding tokens is a design inference, not a tested adapter.
- Slurm single-node deployment is conceptually possible; its documented root slurmd/cgroup model fails the brief’s no-assumed-root-daemon fit. WSL dxg device isolation and NVML autodetection remain unevaluated; Linux cgroup support alone does not prove them.
- MPS consumer-GPU/WSL compatibility, MPS OSS license status and v3 dxg availability remain unevaluated. Linux-driver cgroup documentation must not be transferred to WSL’s Windows driver by assumption.
- gpusched is a serious R2 alternative, but WSL process telemetry limitations [W1], multiple scheduler instances, escape into systemd scopes and crash-safe reservation release remain unevaluated. Its README’s broad memory-enforcement limitation is not adopted: M2 documents a newer counterexample.
- dgxtop’s dated rendered and raw README responses differed. No version-specific guarantee or source-level absence finding rests on it. WSL monitoring exists; exact detector functionality remains unevaluated.
- Microsoft/NVIDIA guides reviewed do not describe the required dxg persistence gate. Upstream issue observations are primary reports with uncontrolled confounders, not an official supported detection contract. Broader WSL-health-tool recall and standalone novelty remain unevaluated.
- No soks distillation, code/config changes, installs, candidate runs, commits, push or deployment. No tool release/version/changelog/changeset is applicable: this deliverable is a dated survey only.
