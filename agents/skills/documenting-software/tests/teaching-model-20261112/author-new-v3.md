# Rill ドキュメント計画

| ページ | 答える問い | 読者の到達点 |
|---|---|---|
| README | Rill は何を受け取り、何を返すか | 用途と対象外（DB 書き込みは行わない）を判断できる |
| クイックスタート | 最初のレコードまでに何が起きるか | 最小例を動かし、結果が検証済みレコードだと言える |
| 解説: 三つの段階 | バイト・セル・レコードはどう違うか | 失敗がどの段階で起きたかを切り分けられる |
| 解説: 途中停止と再開 | 途中で止めたら、どこから再開できるか | 再開の限界と、冪等化の責任が呼び出し側にあると説明できる |
| Schema ガイド | 型付きの値はどう得るか | 実行時の Schema と静的型の違いを誤らずに選べる |
| API リファレンス | 個々の操作の正確な仕様は何か | 必要な項目を素早く引ける |

## 解説の冒頭: 行の途中で切れた入力は、どこまで読めたのか

Rill はバイト列を任意の位置で分割されても、行を正しく取り出す。ここでは次の入力を例にする。

```
名前,備考\n山田,"改行を含む\n備考"\n
```

転送層が「山」の途中でチャンクを切ったとする。デコーダは未完成のバイトと引用符の状態を保持し、次のチャンクと合わせて文字を復元する。引用符の中の改行は行の区切りとして扱われないため、`山田,"改行を含む\n備考"` は行の終端を認識した時点で一行にまとめられ、セル `["山田", "改行を含む\n備考"]` として出てくる。

この段階ではまだ型は付いていない。次に Schema が列数を確認し、各セルを変換して制約を検査する。通ったものだけが検証済みレコードとして非同期イテレータから届く。

条件を変えてみる。入力が引用符を閉じないまま終わると、finish は型付きのエラーを返し、その行は有効なレコードとしては返らない。完了していた前の行は、区切りを認識した時点で既に届いている。したがって、読者が次に確認すべきことは「前の行がデータベースに書かれたか」である。この点は Rill からは分からない。書き込みと再試行、重複排除は呼び出し側の責任であり、Rill は外部の書き込みを確定させることも、正確に一度だけ実行されることも約束しない。

さらに、途中のバイトオフセットで再開しようとすると危険である。オフセットだけでは、引用符の状態、UTF-8 の未完成バイト、ヘッダの状態が分からないからだ。Rill はオフセットを保存する仕組みを提供しないので、再開は入力全体を読み直す前提で設計する。
