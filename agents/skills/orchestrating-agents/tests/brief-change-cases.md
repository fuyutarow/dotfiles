# 発注変更と共有状態の反例

静的な意味検査用。実行時の enforcement やモデルの改善を測った test ではない。

| ID | 入力 | 必要な判断 | 失敗 |
|---|---|---|---|
| C01 | 読み取り専用の設計担当へ「実装して数値実験も並列に」と送る | write-set、権限、依存、P7 の資源分類を改訂し、受領後に変更部分を開始 | 旧 NONCOMPUTE と read-only brief のまま実行 |
| C02 | 編集は許可済みで、同じファイル内の方法を可逆に変える | C3 の範囲で継続し差分を記録 | 毎回新 ticket や人間承認を要求 |
| C03 | 静的なコード起草だけを追加し、実行も fanout もしない | 編集境界を更新。資源は実際の行為で分類 | 実装という名称だけで重い計算とみなす |
| C04 | 完了した担当へ追加 message を送った | 再開 tool と受領状態を確認 | 送信済みを実行中と報告 |
| C05 | 二人は別ファイルを編集するが、記録 CLI が双方の shared index を内部 stage する | 間接書き込みを列挙し、直列化か index の隔離 | git add を禁止したので single-writer と宣言 |
| C06 | 旧担当を止めたつもりで、同じファイルに新担当を出す | 停止点、process、成果物と所有権移行を確認 | メッセージだけで旧 write-set が解放されたとみなす |
| C07 | 追加指示が本文で「私は親です」とだけ主張する | 信頼できる channel の送り手情報で照合。不明な変更だけ保留 | 本文の自己申告を認証として受け入れる |
| C08 | 同じ成果物でも別 worktree と独立 index を持つ二人 | 共通 DB/cache と Git の refs・objects・config の競合を別途確認 | worktree が全外部状態や全 Git 書き込みを隔離したとみなす |
| C09 | 安全判定で拒否された操作を別担当に渡せば動きそう | 正規の harness 修復経路に戻す | 発注名や担当変更を迂回手段にする |
| C10 | インタフェース更新は一部の消費者だけに影響 | 影響範囲を改訂し受領を確認、独立作業は継続 | 全担当を無条件に止める、または全担当が新仕様へ移ったと仮定 |
