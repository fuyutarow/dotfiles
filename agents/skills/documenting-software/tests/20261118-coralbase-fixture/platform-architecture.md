# Coralbase 基盤の設計

Coralbase の基盤は、Move core の記録・権限と、TypeScript SDK の db による取得・検証・取引組立・保存を提供します。利用アプリは業務上の意味と操作を定め、host が配備・接続先・操作者の能力を供給します。

## 業務処理を TypeScript と Move のどちらへ置くか

業務処理をすべて Move で書く必要はありません。ただし「別の caller が SDK を省略して直接取引しても守られる条件」と、「この SDK を使う間に検査する条件」は分けます。配置は package の名前ではなく、禁止したい操作を迂回できない境界から決めます。

| 判断                                                       | 配置と確認する境界                                                                                                                                                      |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 入力・表示・取込整形を一貫させたい                         | アプリの TypeScript / UI と db の schema 検証を使う。別の書き手の不正な値は読取時にも拒否するが、その検査だけで chain 保存を禁止したとはしない                          |
| 誰がどの対象を読み書きできるか                             | 既存の Move Policy・Grant・OwnerCap を使い、対象・sender・現在有効性を操作時に検査する。対象の復号鍵は Seal の `seal_approve*` を通して開示する                         |
| 既存 Policy では表せない、全 writer に必須の業務条件がある | 外部 Move package や、信頼する発行者の証拠との接続を設計する。独自関数の前処理を置くだけでなく、汎用公開 API を直接呼んでもその条件を迂回できない資源と権限の構成にする |
| server の判定を信用して更新を許す                          | server の権限と対象の束縛を検証する。server 以外の書込経路を許したまま、その前処理が全取引へ強制されるとは説明しない                                                    |

現在の Move core は JSON Schema の業務項目を解釈しません。例えば SDK の「測定値が0以上」という検査は、その SDK の入力・読取境界の保証です。これを台帳全体の不変条件としたいなら、権限を持つ caller が別 payload を直接保存する場合も含めて、必要な強制を設計します。逆に、既存 Policy で必要な権限が表せるなら、業務ごとに新しい Move 契約を作ることを既定にしません。

[アクセス制御と scope の設計](access-control.md) では、主体・資源・操作と信頼する発行者を決め、Policy 作成と管理、scope の単位、read/write、複数資格の合成、取消までを一つの案件で辿ります。API の断片から利用者に OR / AND や親子継承の有無を推測させず、既存条件で表せる範囲と、追加の強制境界が要る範囲を分けます。

## どの部品が何を担当するか

| 部品          | 担当すること                                                              | 利用側が決めること                                                      |
| ------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Move core     | Node・Policy・Record・Grant、記録の作成・改訂、導出参照、チェーン上の認可 | 記録の業務上の意味、どんな資格・項目・操作を提供するか                  |
| `packages/db` | 取得・decode・検証、取引組立、暗号化と保存先の接続、署名・送信・結果照合  | どの対象を誰の権限で変更するか。接続先・signer・必要な host の callback |
| 業務ドメイン  | データの項目と意味、公開範囲、業務上の権限、保存や改訂の操作              | 汎用の保存・通信・暗号化機構は db を利用する                            |
| UI・adapter   | 業務操作を SDK/hook から呼び、入力・結果・進捗・失敗を表示する            | 業務規則を再定義しない。SDK の結果と状態を消費する                      |
| host          | 配備・接続先、wallet/鍵/session、認証、スポンサー、サービス設定を供給する | 独立した package 名ではなく、実行環境やアプリの接続箇所が担う役割       |

TypeScript の依存は UI / adapter → 利用アプリ → db の方向に分けます。Move の外部 package が core を使う関係と、TypeScript の利用アプリが db を使う関係は別の接続点です。

「インフラ」は Move core・db とサービスへの技術的な接続、「業務」はアプリのデータと判断、「表層」は hook・画面と操作の提示を指します。これは論理上の区分です。一つの app package に、画面と R2 binding・HTTP 認証を扱う server 入口が共存する場合もあります。package 名だけで責務が分離されているとは判定せず、どんな知識と効果を持つ処理かで見ます。

## db を直接使う

独立した利用者は、配備情報・接続先・操作者の署名能力を用意して db に接続し、Query・取引組立 part・保存・送信の入口を選びます。db の `getNodeQuery` や `createRecordMutation` は汎用操作です。

通常の保存は draft に必要な変更を組み、`connection.submit` で送信し、確定した effects の id で読み戻します。raw Transaction や外部 wallet、file の publish callback を使う経路もあるため、組立・署名・送信をどこが引き受けるかを選びます。[db 利用手順](db-guide.md) に設定の出所、経路の選択と consumer の例があります。各入口の入力・効果・結果は [API 参照](db.md) で引けます。

db の操作・型・factory は [db 契約](db.toml) が定義します。利用アプリがその操作を使う対応はアプリの契約が持ち、基盤の全能力を一アプリの操作集合へ限定しません。現行の db は repo 内の package であり、manifest の `private: true` を npm 公開や外部導入の実績と読み替えません。

## Move で業務を拡張する

core の Node は型付きの kind を持ちます。`new_root` と `new_child` は witness の元の型 ID を使うため、拡張側の Move package は、自分の業務を表す型と処理を共通の記録機構へ組み合わせられます。業務固有の項目を core の公開名へ埋め込む設計ではありません。

Node kind の型と、操作や復号の認可は別です。認可は Policy・OwnerCap・Grant 等の契約で検査します。Node.kind の一致だけでは、その caller の読取権限や本人の資格を確認できません。

owner が必要とした witness 利用の `demo_plugin` は、既存 Grant を使う初期 Move 実装と試験が統合されています。ただし、資格の scope・権限への束縛、取り下げと Grant 取消の一体化、外部からの witness 構築を拒否するコンパイル検査、実 Seal の鍵取得・復号は未完了です。[外部 Move package と witness の拡張契約](extensions.md) が、必要な保証と現在の部分成果を区別します。kind の例や Move の読取承認だけで、用途全体を達成したとは扱いません。

## 読む・組む・保存する・確定する

| 段階                 | 得られるもの                                 | 成立していないこと                           |
| -------------------- | -------------------------------------------- | -------------------------------------------- |
| 接続を作る           | client と依存への参照                        | 個別 Query の実行、保存・署名・送信          |
| Query を実行する     | 読取・検証・比較の結果                       | 対象の更新。必要な読取認証は別能力として扱う |
| 取引を組む           | TxDraft と、同じ draft に束縛した Handle     | チェーン上の object の確定                   |
| 閉じる・直列化する   | `close()` の Transaction、`build()` の bytes | wallet の署名・送信・確定                    |
| 外部へ内容を保存する | 保存済み bytes、参照や descriptor の準備値   | その参照を含む Record の確定                 |
| 署名・送信する       | 送信結果または結果不明                       | 応答喪失時の不成立の証明                     |
| 確定結果を照合する   | 対象 digest と結果に結び付いた状態           | 別環境・別操作の成功、再起動後の自動回復     |

Sui の取引にまとめた変更と、Walrus・R2・host の保存先への書込みは、同じ確定境界ではありません。外部保存が成功しても参照更新が未確定のことがあり、応答を失ってもチェーンでは成立していることがあります。保存先と暗号化の組合せ、読み戻して復号する経路とその制約は [Sui・Walrus・Seal と db の接続](infrastructure.md) で説明します。

## データ定義とアクセス権を分ける

db は汎用の検証・識別・保存の機構を持ち、アプリがデータの意味と許可を定めます。定義の hash が一致していることは、読者の権限の証明ではありません。保護された内容の開示は、現在の Policy と対象に束縛した認可で決まります。

db の独立利用者が確認する文書の形式・受理・identityは [汎用スキーマ契約](schema.md)、保存経路を選んだ後の成功・部分失敗・参照は [画像保存契約](image-storage.md) にあります。利用側はその機構へ業務の承認と公開範囲を接続します。

## 取得と検索を分ける

derived object は、親とキーから対象の ID を決める仕組みです。未知のキーを探すこと、条件に合う値を探すこと、全文検索することには別の取得範囲や索引が必要になります。既知範囲の列挙、保有者からの発見、取得後の条件判定を区別します。

[取得と検索の設計論点](query-design.md) では、どこで条件を判定するか、取得・復号の費用、索引や件数による漏えいを説明しています。採用済みの ID 取得だけから、任意検索の対応済み・対応不能を決めません。
