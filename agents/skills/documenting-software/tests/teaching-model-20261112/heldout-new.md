# Gatelet を使い始める

## ページ計画

| # | ページ | 答える問い | 読者が得る結果 |
|---|---|---|---|
| 1 | 概要 | Gatelet は何をし、何をしないか | 純粋な判定器だと説明でき、認証・保存・強制が範囲外だと分かる |
| 2 | 判定の仕組み | policy と grant から true/false はどう決まるか | read/write のリスト、OR、空は拒否、Owner/Grant の一致を手で追える |
| 3 | grant の変化と再評価 | grant を一つ外すと何が変わるか | 候補ごとの独立評価と、スナップショットの再評価が必要だと判断できる |
| 4 | アプリへの組み込み | 判定をどこで、誰が行うか | 保護操作の直前で判定し、認証と grant 発行は自アプリの責任と区別できる |
| 5 | 限界と非対象 | 継承・deny・取り消し・キャッシュを扱うか | 扱わない機能を前提にせず、アプリ側で補う範囲を見積もれる |

ページ 1 は他のページの前提なので先頭に置く。ページ 3 と 4 は、読者が「一度 true なら以後も安全」と誤解しやすい箇所を重点的に扱う。

## 説明ページの冒頭: 判定の仕組み

ドキュメント編集アプリで「保存」ボタンを押せるかを考えます。Gatelet は、この問いに真偽値で答える部品です。

Gatelet に渡すものは三つです。認証済みの subject（誰か）、リソースの policy、そして subject の現在の grant のスナップショットです。認証と grant の発行は Gatelet の外側にあり、アプリの責任です。

policy は read と write のクローズの列です。列のどれか一つに一致すれば許可されます（OR）。列が空なら拒否されます。

具体例で考えます。以下のビットの値は説明用の仮定で、ビットの意味はアプリが決めます。

- write policy: `Grant(scope="doc/42", mask=0b0010)`（doc/42 の「編集」ビットを要求）
- grant スナップショット: doc/42 に対する `0b0110`

scope が完全に一致し、マスクの共通ビットは `0b0010` で非ゼロなので true です。ここで注意してほしいのは、要求したすべてのビットを持つ必要はなく、共通のビットが一つでもあれば足りる点です。次に grant を `0b1000` に変えると共通ビットがなくなり false になります。scope が doc/43 なら、ビットが合っていても false です。

true は何の操作も実行しません。評価器は「許可された」と返すだけです。保存処理は、保存を実行する直前に判定結果を確認する必要があります。ここが分かれば、評価器を通ったことと保存が安全に完了したことは別の事柄だと説明できます。
