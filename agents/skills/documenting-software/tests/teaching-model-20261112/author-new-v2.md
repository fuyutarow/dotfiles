## 説明ページ（冒頭）: 三段階で読む CSV

Rill を使うと、ネットワークや一時ファイルから届いた生のバイト列を、アプリケーションの型を持つレコードとして一件ずつ受け取れます。その過程は三段階に分かれています。混同しないことが、Rill を正しく使う第一歩です。

1. **バイト（transport）**: 転送層が `Uint8Array` のチャンクを押し込みます。チャンクの境界は任意の位置に来ます。UTF-8 文字の途中、引用符付きフィールドの途中、行末記号の途中で切れることがあります。引用符の中には改行も含められます。そのため Rill は、未完成のテキストと引用符の状態をプッシュの間保持します。
2. **セル（decode）**: 行区切りを認識した時点で、完成した行がセルの列として出てきます。`decode()` の既定の出力はこの段階で、セルにアプリケーションの型はまだ付いていません。
3. **検証済みレコード（Schema）**: アプリケーションが選んだ runtime Schema が、列数、各フィールドの変換、制約を確かめて値に変えます。ここで初めて、読み手はレコードを業務の値として扱えます。

### 境界を動かすと何が起きるか

- **Schema を変える**と、同じセルでも受理されるレコードが変わります。列数が合わない行、変換に失敗する行、制約に違反する行は、有効な型付きレコードとしては返されません。
- **チャンクの切り方を変える**と、途中の状態が保持されるため、最終的に得られる行は変わりません。ただし、切れ目のバイト位置だけでは、引用符や UTF-8 の途中状態を表せません。これは後で再開位置を扱うときに重要になります。
- **入力が最後まで閉じない**（引用符付きフィールドが閉じないまま終わる）場合、finish 操作は型付きエラーを返します。途中の失敗行は有効なレコードとして渡されません。

### 限界

- Rill は、任意の実行時 Schema から特定の静的なアプリケーション型を推論しません。静的な型が必要なら、固定された TypeScript 型と実行時パーサを一緒に持つコンパイル済み Schema モジュールを使います。
- Rill はバイトオフセットを診断に報告しますが、耐久性のあるパーサの checkpoint や「オフセットからの再開」API はありません。
- データベースへの書き込みは呼び出し側が所有します。Rill は外部 DB への書き込みをコミットせず、exactly-once の外部効果も保証しません。再試行と重複排除は利用者の設計です。
