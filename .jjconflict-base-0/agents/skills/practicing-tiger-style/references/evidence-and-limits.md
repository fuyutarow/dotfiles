# Evidence and limits

> **SOLE owner:** interpretation limits and triggers for revisiting effect claims.
> Source identities and grades live in `source-ledger.md`.

## Use the bounded position

The SoK separates authored prescriptions, adjacent observations, and untested effects.
Use that separation before making a recommendation.

| Evidence available | Permitted conclusion | Not established |
|---|---|---|
| TigerStyle guide | What the authors prescribe for their project | Universal thresholds or measured benefit |
| TigerBeetle architecture account | How one system connects workload to design choices | A topology every TigerStyle user must copy |
| Power of Ten | Safety-critical C rationale and restrictions | Language-independent bans |
| Distributed-system failure study | Error-handling faults in the studied failures | TigerStyle adoption's causal effect |
| Assertion case study | File-level association in two components | A universal assertion quota or causal quality guarantee |

The bounded review located no direct controlled evaluation of this skill's effect on coding agents.
Do not turn that search result into a claim that no such research exists anywhere.
Do not promise improved agent correctness, safety, speed, or research throughput.

The T0 map and T1–T4 ledger are engineered adaptations.
Their usefulness must be checked on the target; they are not experimentally validated TigerBeetle artifacts.

## Interpretation rules

- A planned test is a plan; mark it unrun until an actual result exists.
- A source's local mandate may be supported while its universal translation is unsupported.
- A compiler or passing test establishes only the property that it checks.
- Runtime limits need units, scope, justification, and an overrun outcome.
- A design estimate can guide a prototype; it cannot certify achieved latency or capacity.
- Invalid results may be experimental observations; apply the declared interpretation rule.

## Revisit

Reopen the affected source and ledger rows when one of these changes:

| Trigger | Revalidation |
|---|---|
| New direct comparative evidence | Check comparator, workload, outcome, cost, and uncertainty |
| New runtime or failure consequence | Revisit the applicable design and obligation rows |
| Failed independent check | Reopen the earliest unsupported design assumption |
| Changed source revision | Check affected prescriptions against the new revision |
| Expired exception | Apply the exception lifecycle in the ledger reference |

Adjacent LLM benchmark claims from the historical skill are not active premises here.
Recover their old bibliography from Git history if a new bounded survey needs them.
