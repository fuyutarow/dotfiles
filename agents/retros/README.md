# Dotfiles retrospectives

retro ファイルは、dotfiles の作業で起きた問題、提案、良かった点を残す振り返りの Markdown 記録。所有者は dotfiles owner。原文と負の結果を保持し、各課題に追跡用の ID・状態・原則（その課題が教えること）を付ける。過去の記録は解決後も残す。

## ID と記録の扱い

ID は `R2610-0A-A1` / `R2610-0B-A1` の形式。`2610-0` は retro の版、`A` / `B` は part 1 / part 2、末尾は原文の節・項目番号を表す。同じ ID は状態更新後も変えず、再利用しない。原文に番号のない part 2 の D・F は `D1`・`F1` とした。part 1 の `X1` は coordinator の状態指定にだけある jj-in-sandbox conflicts の追記で、原文由来の課題と区別する。

課題数は ID の数。複合課題は一つと数え、状態欄で内訳を示す。part 1 は原文の 17 課題と追記 1 課題、part 2 は 11 課題。良かった点（part 2 の E1 を含む）は原文を残し、対応課題として数えない。

## 状態の更新

- `fixed — commit: <hash>`: 修正された課題。修正を確認できたコミットを記載する。
- `in progress — ticket: <name>`: 着手中の課題。追跡できる票名を記載する。
- `open`: 未着手、または解決・着手の根拠がまだない課題。着手予定や依存先があれば併記する。予定だけで `in progress` にしない。

初期状態は 2026-10-11 時点の coordinator の申告に基づき、コミット・票の実在や修正内容はこの保存作業で独立検証していない。状態指定がない課題は `open` とした。part 1 A2 は抽選修正が `fixed`、予算対応が `open`。part 2 B3 の reclaim redesign は `reclaim_progress` 完了後の予定で、専用票名は未提示。

owner または owner の指示を受けた担当が、該当 ID の状態欄を同じファイル内で更新する。更新日、確認したコミット・票・検証結果をその項目に追記し、変更前の状態と根拠も履歴として残す。再発時は `open` または `in progress` に戻し、再発の根拠を残す。複合課題は内訳ごとに更新し、一部の修正で全体を解決済みにしない。

原文の観察・提案は書き換えず、訂正が必要なら日付と根拠付きの注記を追加する。原則は保存時に補った教訓で、実装済み規則を意味しない。新しい retro を保存したらこの索引にリンクを追加する。今回の版は指定の `2610.0` を使い、変更の説明はこの索引と各記録に置く。
