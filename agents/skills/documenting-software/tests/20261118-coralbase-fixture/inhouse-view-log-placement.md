# 閲覧履歴をどこに置くか：費用と信頼境界を比べる

資料を読むQueryと、閲覧したという申告を保存するMutationは別です。現行の文化継承アプリでは、記録対象の保護層を開いた後に、本人署名の閲覧記録をオンチェーンへ送ります。その送信にはgasが必要で、現在はスポンサーが負担します。本書は、閲覧者の操作負担、記録の総費用、保存・秘匿の信頼境界を比べ、置き場所を判断するための設計比較です。

要求を変える文書ではありません。現行の要求は、閲覧履歴を本人が署名した暗号化オンチェーン記録とする [I-VIEWLOG](../heritage/product.toml) で、その採用の記録は [採用済みの判断](../heritage/decisions.md) にあります。置き場所を変えるかどうかは owner と PO が決めます。

## 1. 読むだけの場合と、記録する場合を比べる

寄付者が、ある資料の「寄付の記録」を開く場面で比べます。

| 起きること          | 読むだけ                                                  | 現行（閲覧履歴を書く）                                     |
| ------------------- | --------------------------------------------------------- | ---------------------------------------------------------- |
| 利用者の署名        | 必要時にSealの読取sessionを認証し、有効期間内は再利用する | 左に加えて、記録対象の開封を記録する取引へ署名する         |
| Sui への取引の送信  | Queryからの送信はなし。鍵サーバーは承認を試し実行する     | 記録対象の開封に対して送信する。同じページ・資料・層は一回 |
| gasの負担           | 読取Queryからのchain送信gasはなし                         | 記録取引ごとに発生し、現在はスポンサーが負担する           |
| 追加の公開chain記録 | 閲覧記録を追加しない                                      | 送信者address・取引時刻・索引等の情報が公開される          |
| 保存する申告        | UC11の記録は保存しない                                    | 暗号化したRecordと索引、確定した取引履歴                   |

この表は効果の種類を比べるもので、walletの確認画面や署名promptの回数を実測したものではありません。公開層だけの閲覧と財団自身の閲覧は記録対象外です。chainへの追加記録がないことも、鍵サーバーやRPCに要求が見えないこと、サービス運転費用がゼロであることを意味しません。

読むだけの経路は、[操作と効果](../heritage/effects.md) が UC2 について「取引署名・送信をしない」と定めるとおりです。鍵の取得の仕組みは [Seal の解説](../mysten/seal.md) にあります。右の列の差は、すべて UC11（閲覧の記録）が加えているものです。

## 2. 現行の記録は何を確かめ、何を確かめないか

現行の流れは次のとおりです。

1. 利用者が画面で保護された層を開く操作をします。
2. アプリがその層の復号を試み、成功した層のうち公開以外を拾います。公開層だけの場合と、財団本人の場合は記録しません（`packages/heritage/src/usecases/attest-view.ts`）。
3. 閲覧者のブラウザが、資料・層・本人・時刻を入れた記録を暗号化します。読めるのは本人と財団です（journal の Policy は read が Owner と Writer、`setup-view-journal.ts`）。
4. 閲覧者本人が取引に署名し、journal へ 1 件書きます。書くには journal 用の Grant が要り、証の発行と協力者の許可が同じ取引で配ります（`issuance-rule.ts`、`collaborator-rule.ts`、`packages/db/src/attest/index.ts`）。

この記録は閲覧者のクライアントによる自己申告です。条件を変えると、次のことが起きます。

| 場面                                         | 結果                                                                              |
| -------------------------------------------- | --------------------------------------------------------------------------------- |
| 正規の画面で開き、記録の取引に署名する       | 取引が確定すると1件が追記される。署名だけで記録成功とはしない                     |
| 記録の署名を取り消す                         | 本文は既に復号できている。記録は残らない                                          |
| 改造したクライアントでUC11を呼ばず復号する   | 復号できても閲覧記録の取引は送られない。鍵要求の観測と公開chainへの記録は別である |
| Grant を持つ人が、見ていない資料の記録を書く | 追記される。chain は暗号文の中身を検査できない                                    |

I-VIEWLOG自身が「記録は本人の申告であり、復号の暗号学的証明ではない」と述べています。本人署名と取引の確定は、誰が何を送ったかを検証する根拠にはなりますが、その人が実際に読んだことや、全ての閲覧が記録されたことの証明にはなりません。

現行のAttestEntryはimmutableですが、参照するRecordは閲覧者所有の通常のRecordです。coreのupdate_record入口があるため、索引の不変性を本文の変更不能性と同一視できません。確定済みの取引履歴が書き換わらないことと、最新本文が変わらないこと、履歴本文を将来も取得できることも別です。保存先を単独のアプリ運営者に置かなくても、RPC等の取得経路への依存まで無くなるとは保証しません。

## 3. 論点：書くことの費用と、読むことの費用を分ける

owner は 2026-11-12 に次の考えを示しました。**書くことに費用がかかるのは受け入れる。読むことに追加の費用がかかるのは不合理である。**

資料の投入・編集・証の発行は、状態を変える操作で、署名と手数料を伴うことに理由があります。閲覧は状態を変えません。閲覧に署名・手数料・公開の痕跡を足しているのは、閲覧そのものではなく、記録の置き場所の選択です。

本人が自分の閲覧を振り返る用途と、財団が資料への関心を知る用途を考えます。申告を預かる運営者を信頼する設計も候補ですが、本人署名の検証可能性、本人と財団だけが読めること、保存・削除・可用性の条件を別に評価します。この用途に対して、閲覧者の署名・操作負担、スポンサーを含む記録の総費用、公開される情報が釣り合うかが判断の中心です。

代理送信で閲覧者の取引署名を減らしても、chainへの書込みgasは消えません。現在も閲覧者はgasを直接支払っていないため、Cを「読む人の費用が新たにゼロになる」とは比較しません。ownerの発言を、どの費用・負担を減らす判断へ適用するかは、この比較を踏まえて決めます。

## 4. 選べる置き場所

| 選択肢                                    | 読む人の負担                     | 得るもの                             | 引き受けるもの                                                                              | 状態           |
| ----------------------------------------- | -------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------- | -------------- |
| A. オンチェーン、開封ごとに本人が送る     | 記録対象の開封取引へ署名する     | 記録用の別のオフチェーン保存先が不要 | スポンサーのgas、公開chainの情報。本文不変・永久取得の保証とは別                            | 現行・実装済み |
| B. オンチェーン、本人がまとめて送る       | 区切りごとに記録取引へ署名する   | 複数記録を一つの取引にできる可能性   | 保存前に画面を閉じる場合の欠落、送信待ちの保持、取引サイズ上限。gas削減量は未測定           | 未実装         |
| C. オンチェーン、申告を預かって代理で送る | 申告の認証。署名単位は未決       | 閲覧者によるchain取引署名を避ける    | serverの認証・保存・代理送信。gasは残り、writerと本人の読取条件の再設計が要る               | 未実装         |
| D. オフチェーンの保存先                   | 申告の認証。署名単位は未決       | 記録のchain送信とgasを無くせる       | server/保存の運転費用、秘匿・改変検知・削除・可用性の設計。通信の痕跡まで消えるわけではない | 未実装         |
| E. 自前の鍵サーバーで鍵要求を記録する     | 通常の読取認証に加える操作は未決 | サーバーに届いた鍵要求を観測できる   | サーバー運用・閾値と秘匿の前提。鍵要求と閲覧は一致しない                                    | 未検討         |
| F. 記録しない                             | 記録のための追加操作なし         | 記録の運転・保存費用を避ける         | 閲覧履歴の二つの用途を失う。通常の認証・通信費用は残る                                      | 要求の変更     |

BからEは、コードと契約から組み立てた案です。実装も計測もしていません。Eで得られるのは鍵要求の観測です。鍵を取得しても閲覧しない場合や、取得済みの鍵で再度開き、新しい要求を出さない場合があります。各サーバーで見える要求・認証主体の範囲、資料との対応、閾値構成をまたぐ欠落・重複の扱いは未検証です。「鍵サーバーだけが観測できる」「実閲覧の完全な証明になる」とは主張しません。

Aを続けることと、索引の責務だけをpluginへ移すことは別の判断です。Bでは記録の時点・件数・成功表示、Cでは本人署名とwriter・読者、Dではオンチェーン保存と秘匿・保存責任、Eでは記録する出来事そのものが現行契約から変わり得ます。採用前にI-VIEWLOG・UC5/UC11の対応を確定します。Fだけが要求変更を伴う、という表ではありません。

## 5. オンチェーンで続ける場合の具体的な設計

オンチェーンを選ぶ場合に、設計が無いわけではありません。次の構成を記録しておきます。

### 現行の構成（A）

- 財団の root の下に journal 用の Node を置き、その Node に Policy を 1 つ作ります。read は Owner と Writer、write はその Node の Grant です。
- 記録1件は、閲覧者が所有する暗号化Recordです。entryは乱数で、資料との対応を暗号化本文へ入れます。I-VIEWLOGは公開索引から第三者が「誰がどの資料を見たか」を復元できる形を禁じています。この構成の説明を、全ての取引・通信からの情報漏洩を検証した結果にはしません。
- core の `record::new_attest_record` が、Record の作成と同じ取引で、journal の Node の連番へ索引を 1 件追記します。財団は、この連番を辿って全件を列挙します。別のオフチェーンindexerは使いません。
- 取引はスポンサーが手数料を負担します（[I-SPONSOR-ALLOWLIST](../heritage/product.toml)）。

### 索引を plugin へ切り離す構成

閲覧履歴の条件と索引を汎用coreから分ける案です。同じPolicyに対して索引なしのrecord::new_recordを直接呼べるため、初期coreも全てのraw書込みへ索引の追加を強制してはいません。ただし、その事実だけで移管前後の保証の同等性を証明したことにはなりません。正式な入口の原子性・認可・秘匿・有界照会と、consumerの接続を別々に確かめます。この切り離しは今回は行わず、配置の決定と代替経路の受入れまで現行APIを残します。

- plugin が自分の Journal object を持ち、連番と索引をそこに置きます。core の Node の連番は使いません。
- plugin の正式な記録の入口は、core の Record の作成と、Journal への索引の追記を 1 つの取引で行います。索引を通さずに作った Record は、公式の閲覧履歴に数えません。
- TypeScript 側では、汎用 db が plugin の binding を import しない向きを保ちます。plugin 専用の組立と索引の読取は、アプリ側に置きます。
- plugin案を採る場合は、配備・bindingの生成・スポンサーの許可表へ別packageとして接続します。ここで扱う専用Journal pluginは未実装・未配備です。他の外部packageの有無を断定する記述ではありません。

### 読む人の負担を減らす変形（B・C）

- **まとめて送る（B）**: クライアントが開封の申告をため、区切りごとに送る案です。1取引に現行形式のRecordを複数作るなら、PolicyとGrantを再利用する案が考えられます。一つのRecordへ複数の開封を入れるなら、本文schema・照会・件数の意味も変わるため、同じ契約とはみなしません。どちらを選ぶか、送信前に閉じた場合の保存・失敗表示も未決です。
- **代理で送る（C）**: 閲覧者は申告に個人メッセージで署名するだけにし、財団側の server が取引を送ります。書く主体が財団になるので、read を Writer に頼る現行の Policy では本人が読めません。本人宛ての読取条件（本人の Grant を read に受け入れる等）を持つ Policy に作り直す必要があります。

## 6. オフチェーンにする場合に決めること

D を選ぶ場合、保存先を決めるだけでは足りません。

- **誰の申告かを確かめる方法。** 現行の記録は本人の取引署名を使い、記録用HTTP sessionを前提にしません。旧D1と一緒にHTTP sessionをやめたという説明は初稿作者によるもので、当時の実装・原会話は未回収です。新案では旧経路の復活を前提にせず、例えば画像のPUTで使う方式（本人の署名でsender・origin・network・期限を束縛し、回数を制限する。[I-IMAGE-PUT-BOUNDED](../heritage/product.toml)）を記録用に設計できるかを検討します。
- **何を保存成功とし、誰が読めるか。** 受信しただけか永続化まで確認するか、結果不明時の再送と重複、本人と当該財団への照会認可を決めます。画像用proofをそのまま受理する決定ではなく、申告本文・記録用途との束縛とreplayの扱いも要ります。本人Uの認証が成功しても、別人Vの記録を照会できてよいことにはなりません。
- **運営者に内容が見えるか。** 現行は本人と財団だけが読めます。平文で保存すれば、保存先を運用する側も「誰がどの資料を見たか」を読めます。避けるなら、クライアントで本人と財団宛てに暗号化します。Seal の現行の承認は chain 上の Record の実在を条件にするため、chain に Record を置かない記録へそのまま使えるかは未確認です。
- **保存期間と削除。** 削除を許すなら、誰が要求・実行でき、索引・複製・backupまでどこを対象にするかを決めます。保存先がオフチェーンというだけでは、完全消去の保証にはなりません。
- **既存の方針との関係。** 記録済みの11-08の決定はD1を不採用とし、I-VIEWLOGを暗号化オンチェーン保存としています。Dはその保存方式を変更する判断です。この決定から、別用途を含む全てのオフチェーン保存が禁止されたとは一般化しません。

## 7. 決まっていないこと

- 置き場所をどれにするか。現行の要求は A のままです。
- A を続ける場合に、索引を plugin へ切り離すか。
- D を選ぶ場合の、認証・暗号化・保存期間。
- 当時 D1 をやめた理由のうち、保存先を持たないこと以外に何があったか。本書の作者は、11-08 の議論の原文と、当時の D1 の実装を読んでいません。
