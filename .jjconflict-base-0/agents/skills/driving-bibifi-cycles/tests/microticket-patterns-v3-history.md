# Microticket patterns — choose a slice that can finish a BIBIFI loop

Use the current goal and evidence to select a pattern. Do not create all of these tickets by default.
Each row includes a useful decision; finishing a document or opening a process alone is insufficient.

| Broad work request | Small Build | Break / baseline / control | Fix or close / next decision |
|---|---|---|---|
| Build the whole new learner | Bind one minimal component to its real consumer with exact constructor/API names | Tiny input reaches the intended model, update and scorer; a different model ID must not silently use the old implementation | Repair dispatch/interface or retain the witnessed path; next test can measure that component |
| Port the whole learner to GPU | Run one necessary operation/small target slice on device | Compare the pinned reference and device outputs at relevant positions/state boundaries | Fix first divergence or retain this limited parity result; expand only the next useful slice |
| Test a proposed mechanism | Smallest matched ON/OFF implementation or fixed oracle intervention | Prewritten scoped prediction, same-stream baseline and informative control | Retain/reject/narrow that mechanism claim, or diagnose the named confound |
| Await a large component hand-back | Deliver one interface plus a consumer probe | Consumer calls the expected type/signature; no compile-only substitute for the claimed runtime behavior | Release the checked seam to its dependents; preserve unfinished implementation as open |
| Investigate a slow test cycle | Reproduce one cold/warm startup or measured hot phase | Timing and bound against the same workload; separate compile, preparation and kernel | Reuse preparation or change the measured bottleneck; do not promise speedup from line counts |
| Research while an experiment runs | Check one load-bearing premise/source statement | Exact primary-source locus and applicability/counterexample check | Return a supported/scoped/open premise and its effect on an authorized next branch |

A data-only oracle is still computational work and needs the relevant resource admission.
A source lookup or theory task has an owner, deadline and hand-back artifact even when it needs no numerical run.
Do not reinterpret raw/invalid measurements as a scientific result; consume the evidence owner's disposition.

## Pick the dependency that actually binds

Before blocking a ticket, complete: “Without X, action Y cannot produce observation Z because …”.
If only a broader claim needs X, choose a diagnostic Z that can be interpreted now.
If no useful Z survives the missing premise, repair X rather than launching speculative batches.

| Example | Correct dependency |
|---|---|
| Constructor absent; target entrypoint throws | Execution blocker: build the smallest callable component/consumer pair |
| Selected model is never called by the runner | Target-identity diagnostic first; a score from the old model says nothing about the selected one |
| CPU/GPU parity unknown | A parity diagnostic can run; a preserved-capability claim waits for its required result |
| Full suite not yet accepted | An independently interpretable component experiment may run; no whole-suite achievement claim |
| Test B requires a parameter chosen from A | Prepare B's conditional branches; choose and freeze B after A's result |
| Two fixed arms share a valid frozen protocol | They may run concurrently if resource and mutable-state constraints allow |

Section-governed work keeps its WIP/admission unit. Multiple arms of one admitted test follow that contract.
A second independent test needs its own permitted slot/admission.
Ordinary authorized work does not acquire section authority here.

## Preserve scientific usefulness when shrinking

Preserve the mechanism's minimum depth, its control and the scored quantity when shrinking a test.
If the prediction gap vanishes, choose another witness or a more useful enabling question.
A long setup can be prepared/reused under a finite owner contract.
Count that time in the whole cycle even when the kernel is tiny.
Do not relabel the same unchanged blocker as a new cycle each report.
No parameter/seed sweep or full battery is hidden behind many nominal “micro” IDs.
Larger confirmation needs a separate authorized plan; continue independent useful microtickets where permitted.

## Constructed six-minute window

This is a scheduling example. Times, resources and observations are fictional, not measured predictions.
Goal: produce the first valid result through a new tabular model's actual GPU path.
At 09:00 JST: 24 GiB host RAM and 8 GiB VRAM are available, six CPU threads are available, and GPU compute is idle.
Reserve 4 GiB RAM, 4 GiB VRAM and two CPU threads for the next critical GPU probe.

| Ticket | Why / loop | Footprint / deadline | Action |
|---|---|---|---|
| C1, critical | Build one constructor/consumer pair; break with wrong-model dispatch; repair or retain the path | 2 CPU threads, 2 GiB RAM, no GPU; return by 09:02 | Start now |
| U1, independent | Existing authorized device operation: test its boundary case on an immutable, separate snapshot | 1 CPU thread, 2 GiB RAM, 2 GiB VRAM; return by 09:01, safe stop/release if C2 becomes ready sooner | Use spare GPU capacity now without holding C2's reservation |
| U2, independent | Check the oracle's assumption in one primary source and return its applicability | No numerical process; finite return by 09:03 | Use independent researcher time now |
| C2, conditional critical | Tiny new-model GPU update/scoring fixture using C1's checked interface | 2 CPU threads, 4 GiB RAM, 4 GiB VRAM; experiment target ~2 min, max10 | Launch immediately when C1 and execution requirements pass |

Example event response:

- 09:01: U1 returns its scoped result and releases resources; no wait for the report window.
- 09:02: C1 passes. Launch C2 now; U2 may continue independently.
- If C1 instead exposes a type mismatch, fix that witness; do not start C2 or merely shift its ETA.
- If C2 saturates GPU compute, leave remaining VRAM unfilled and use ready CPU work; memory is not compute capacity.
- At 09:06, report completed artifacts/decisions and actual costs, then the current queue and release ETA differences.
- If C2 is still running below its cap, report its phase and continue nonconflicting work.
  Report time alone does not stop the job.

## Finite workers and reservation release

A worker may run an authorized finite queue while rechecking each next ticket against current findings.
It need not return for permission after every loop, but must receive relevant invalidations promptly.
The queue has a bounded lifetime and event hand-backs. Each experiment retains its own wall cap.
At a cap/stall/deadline, the resource owner stops the process tree and reports peak/release evidence.
An agent finishing its text response does not prove its subprocess or device allocation ended.
Ready successors consume released resources only after that release is observed.
For warm reuse, pin code/config/data and reset mutable experiment state; account for retained memory throughout.

## A fast result can obsolete another worker's whole assignment

Suppose A tests whether a representation can express the target, while B plans a full optimizer for it.
Separate files and free GPU memory make the jobs executable together; they do not make B's purpose independent.
If A will answer shortly, do not assign B the whole optimizer.
Give B only a small useful interface/witness whose result survives either outcome, or select another useful task.
If A rejects the representation, notify B and cancel affected running/queued work through its owner immediately.
Preserve partial evidence and reclaim resources. Do not wait for B's deadline or the next six-minute report.
If A instead supports the representation, select B's next microticket using that result.
An unrelated ticket with unchanged premises continues; every result does not stop the entire fleet.

## Broad agent work while compute is scarce

A long throughput-inventory assignment can become independent short returns from relevant historical records.
Each worker returns the located primitive, matched workload/semantics and one current transfer obstacle.
Other workers can construct a repeated-key batching counterexample, check reset boundaries or inspect a consumer seam.
These are distinct questions with immediate consumers, not replicas of the same broad research prompt.
Launch all useful ready slices that fit agent slots and host limits; do not hold them behind a GPU test.
Where patches share a target file, use isolated proposals and one live integration owner.
Admit each numerical check separately under P7 when it is ready; no hidden compute under a NONCOMPUTE declaration.
Consume returns individually and invalidate only affected branches; do not wait for a complete inventory document.
