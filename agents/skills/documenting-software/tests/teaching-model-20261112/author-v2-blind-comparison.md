# 判定: A と B の盲検比較（Rill 説明ページ）

## 結論

A が B より明確に優れるとは言えないが、初学者向けの変化ケースの説明では A の方がやや有用である。どちらも基準の必須要素を満たさず、A も B も「勝者」とは判定しない。

## A の強み（facts に根拠）

- 「境界を動かすと何が起きるか」の節で、Schema の変更、チャンクの切り方の変更、入力が閉じないまま終わる場合を分けて説明している。これは基準が求める変化ケースの説明に当たる。
- 「入力が閉じない場合、finish 操作は型付きエラーを返す」「途中の失敗行は有効なレコードとして渡されない」は facts の finish と failed row の記述と一致する。失敗と入力終端の扱いを本文で扱うのは A のみである。
- 静的型の限界（任意の実行時 Schema から静的型を推論しない、コンパイル済み Schema モジュールで固定型を持つ）を本文の限界で明示している。
- 切り方を変えても最終的な行が変わらないと述べる点は、facts の「途中の状態を保持する」から導ける。ただし facts は行の不変性を明示していないため、この一文は推論である。

## B の強み（facts に根拠）

- 「読めた」と「正しい業務データになった」が別の出来事だと述べ、三段階を分ける理由を一文で与えている。これは causal model として簡潔である。
- 利用者の処理中は次のチャンクを要求しない、という consumer pacing を本文に入れている。facts に一致する。
- 再開位置の説明（オフセットだけでは引用符と UTF-8 の状態を表せない）は A と同じく正しい。

## B の欠落

- 変化ケースの節がなく、チャンク分割や Schema 変更が結果にどう効くかを読者が自分で組み立てる必要がある。
- 入力終端のエラー、失敗行の扱い、静的型の限界を本文で説明していない。計画表に載るだけで、説明ページは答えていない。

## 両者に共通する未達

- 基準が求める具体的な分割例（引用符付きフィールド内の改行や UTF-8 の途中切れを一つの例で追う）が、どちらにもない。「切れることもあります」の列挙に留まる。
- 行・列というファイルの見慣れたモデルから出発していない。B の「行も列もありません」は橋渡しの一言にすぎない。A は冒頭で行や列に触れない。
- どちらも API 名を発明しておらず、resumability、静的推論、exactly-once の誤った保証は書いていない。この点は両者とも基準を満たす。

## 判断

A の変化ケースの説明は、B にない失敗・終端・静的型の情報を含み、初学者が境界ごとの影響を言い分けやすい。一方、B の「二つの出来事」の区別と consumer pacing は A より簡潔で明快である。差は一節分であり、どちらも具体例を欠くため、A が「相応に良い」と言える程度に留める。この判定は文章の内容についてのみで、読者が実際に学んだかどうかは測っていない。

## 未確認事項

- 両者とも分割例を欠く。この欠落は説明品質の問題として残る。
- A の「最終的に得られる行は変わりません」は facts からの推論であり、facts に明示はない。
